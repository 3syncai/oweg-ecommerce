# Ecommerce browser notifications

This feature uses the open-source `web-push` library and the existing database/PWA worker plus a dedicated notification worker process. It adds no payment, partner or commission-worker dependency. No subscription or campaign is created automatically. Customers explicitly opt in under Account → Notifications.

## Before enabling production

1. Back up the production database; restore it into an isolated PostgreSQL instance. Apply `my-medusa-store/migrations/web-push.sql` there twice and verify existing commerce tables are unchanged. Do not run the general payment test scripts against production.
2. In `my-medusa-store`, run `node scripts/generate-web-push-keys.cjs` once. The ignored `.env.web-push` file contains private credentials; transfer its values into the backend's existing environment securely. Set a valid monitored `WEB_PUSH_SUBJECT` contact. Optionally set `WEB_PUSH_IMAGE_ORIGINS` to comma-separated exact HTTPS origins for your existing public S3/CDN upload service (no wildcard or signed/query URLs). Do not rotate VAPID keys casually: existing subscriptions depend on them. The generated file is not automatically loaded.
3. With the backup verified and the correct database environment configured, run `node scripts/install-web-push.cjs --apply`. This installs only the four `oweg_push_*` tables/indexes. It does not alter existing wallets/orders or send anything.
4. Build/restart Medusa and deploy the storefront + admin. Configure the same stable VAPID keys on the API and worker. Keep `WEB_PUSH_ENABLED=false` until a designated customer has opted in on the production storefront; valid keys allow opt-in while dispatch remains disabled. Do not start the sending worker yet. In admin, grant Marketing or the narrower Browser notifications responsibility. Existing role rules still apply.
5. Enable `WEB_PUSH_ENABLED=true` in the backend environment, build the backend and run `pm2 start ecosystem.push.config.cjs --only oweg-notification-worker` from `my-medusa-store`. Restart the API with updated environment so its editor sees the configuration. Run `npm run push:worker -- --check` to verify the worker heartbeat, then send a **single-customer test** from admin. Use the storefront's `cus_...` ID, not an admin user ID. Browser permission on the admin domain does not subscribe the storefront.
6. Confirm a test notification appears on an Android browser, desktop browser and an iOS 16.4+ installed Home Screen web app; test open/closed app, click destination, disabled permission, unsubscribe and shared-device logout. Actual OS rendering differs from the illustrative previews. Do not promise a precise OS layout, animation, sound or guaranteed delivery.
7. Verify worker progress using history and the worker-health indicator. Each cycle prepares at most 500 subscriptions and claims at most 10 deliveries. There are at most two simultaneous provider requests, each with a 4s transport timeout, followed by a minimum 2s pause after the cycle. The dedicated database pool has at most three connections. A large campaign intentionally takes multiple cycles; exact duration depends on provider/DB response times. Increase throughput only after measuring API/DB headroom. The API no longer registers a notification-sending scheduled job. Run one worker instance; do not add unbounded dispatch loops.

## Delivery semantics and operations

- Database receipts prevent duplicate campaign/subscription rows. A cross-process advisory lock bounds concurrent dispatch. Interrupted leases recover after two minutes. Temporary network/429/5xx failures retry up to five attempts with exponential backoff. 404/410 subscriptions are disabled.
- Provider acceptance is **not** device delivery, reading or conversion. Queued/accepted/failed and unique notification clicks are separate counts. Click receipts use an opaque random capability token; they never attach customer identifiers to destination URLs. Click tracking is best effort and cannot block navigation; it is not a read receipt.
- A transport request can succeed just before a process/DB failure. Such an uncertain outcome may be retried. Stable campaign tags with `renotify:false` reduce visible duplicates; exactly-once external delivery is not guaranteed.
- Cancellation stops queued work. A notification already in flight or accepted by a provider cannot be recalled. Expiry stops stale campaigns; provider TTL is capped at one day and remaining campaign lifetime.
- Customers are authenticated; endpoint ownership cannot be transferred to another customer. On logout the browser unsubscribes before the existing logout call. Browser settings and OS notification settings can also revoke permission. Shared-device UAT is required before broad rollout.
- Only HTTPS browser push endpoints on the explicit provider allowlist are accepted. New providers require a reviewed allowlist update. Do not use generic user-supplied webhook URLs. Navigation is restricted to relative storefront paths. Optional images use existing public storefront paths or configured public upload origins. Uploads reuse the existing media service; they are not fetched by the dispatch server.
- Endpoint/key material is private; admin history returns aggregate delivery counts, never subscriber endpoints or encryption keys. Do not paste `.env`, raw subscriptions or provider response bodies into logs/support tickets.
- Monitor job failures (`[web-push]`), the age of scheduled campaigns, pending queue age and provider failure rates. Sending is fail-closed if keys are missing or `WEB_PUSH_ENABLED` is not exactly `true`. A stalled worker will leave campaigns queued; PM2 being online alone does not prove progress. The heartbeat must be fresh (under three minutes), with no more recent error.
- To pause delivery, disable `WEB_PUSH_ENABLED` and restart the notification worker and API processes. Keep tables and receipts; do not delete history to retry an uncertain campaign. A new deliberate campaign is a new send.
- Library delivery has no per-message license fee. VPS, database, bandwidth and operational monitoring use existing capacity; this is not a promise of unlimited free throughput.
- The notification worker runs retention cleanup at most once per hour: terminal, expired campaign history older than 90 days is removed in bounded batches (1,000 delivery receipts, 100 empty campaigns, 500 unreferenced inactive subscriptions). Drafts, queued/sending campaigns and recent history are preserved. Existing customer/order/payment/wallet/commission tables are read-only to this cleanup. Old rows may take multiple hourly batches to drain. PostgreSQL can reuse reclaimed space; cleanup does not shrink the RDS allocated-storage setting.

## Scope

Manual/scheduled ecommerce campaigns and per-browser opt-in only. Existing email/SMS/WhatsApp preferences are preserved. Automatic order/payment messages, partner portal campaigns, AI paid APIs, conversion tracking and custom OS action buttons are separate features, not silently enabled here.

## Repeatable development checks

`scripts/web-push.test.cjs` executes the actual routes/dispatcher and migration against an isolated PGLite PostgreSQL engine, with the provider transport mocked. Install `@electric-sql/pglite` in a temporary folder and point `PGLITE_MODULE` at its module directory. Run `node --test scripts/web-push.test.cjs` from the ecommerce root. It never reads `DATABASE_URL`. Session advisory locks are stubbed in this single-connection engine; multi-process lock contention needs a separate disposable PostgreSQL test.

Run `node scripts/web-push.browser.cjs` for intercepted browser fixtures. Set `PLAYWRIGHT_MODULE` and `QA_CHROME_PATH` to your local Playwright module/browser if you are not using the configured Windows test runtime. It checks responsive admin layout, explicit consent, rollback and worker navigation without contacting customers. Lint, frontend/backend TypeScript checks, admin build, storefront build and the existing mocked cart regression suite should also pass before rollout.

## Worker isolation and deployment

Admin/API writes only campaign/subscription data; it does not send provider requests. `oweg-notification-worker` runs independently from `medusa-api`, `oweg-payment-worker` and the partner commission worker, using the same ecommerce code/database. A separate VPS is not required initially, but CPU, database, network and disk are still shared resources: measure real campaign latency and API p95 under controlled load before raising limits.

After changes to sending logic, rebuild the backend and restart **oweg-notification-worker**; restarting only medusa-api does not update this process. Save PM2 state after initial setup. Stop only this named worker to pause notification delivery. The provided config runs one instance, restarts failures, caps memory and allows 30 seconds for shutdown.

For an isolated local database, use `npm run push:worker -- --dev --once` for a deliberate test batch, or omit `--once` for the loop. `--dev` rejects remote database hosts. Sending still requires valid VAPID keys and `WEB_PUSH_ENABLED=true`; do not enable it against the shared live dataset.

The 6,000-recipient test uses an embedded PostgreSQL engine and mocked push providers. It verifies bounded batches, two-request concurrency and unique receipts; it is **not** a benchmark or guarantee of production throughput.

## Verification completed locally (3 November 2026)

- Full backup restored into an isolated PostgreSQL instance; migration applied twice and 230 existing commerce-table fingerprints remained unchanged. The shared database received only the four additive notification tables/indexes; no shared campaign was created or sent.
- Seven automated regression groups passed, including 6,000 mocked recipients in 600 bounded batches, peak provider concurrency two, ownership/RBAC, retries, cancellation and retention. This is a correctness test, not a production load benchmark.
- Mocked browser fixtures passed at 320, 390, 768 and 1280 pixels. Frontend/backend TypeScript passed; storefront lint reported zero errors and 22 existing warnings. Production builds passed.
- On desktop Chrome, the designated customer explicitly opted in. A fresh server-queued push was provider-accepted, appeared in Windows notification centre, and the customer confirmed clicking it opened Account → Notifications. A separate local display test also passed. A missing popup alone did not mean delivery failed.
- The header bell links to Account → Notifications; the old /notifications route redirects there instead of showing a placeholder.
- Production deployment/worker startup and real Android/iOS-device UAT remain operator rollout steps. Codex embedded-browser subscription was rejected; it is not counted as a supported, verified push device. Do not broaden the provider allowlist to arbitrary URLs to accommodate it.

For an existing production installation after merging future notification changes, pull the reviewed code, install locked backend dependencies with the project's chosen package manager, build Medusa, and restart both medusa-api and oweg-notification-worker with updated environment. Deploy the storefront/admin through their existing pipeline. On first installation, follow the key/schema/opt-in/single-customer steps above before enabling a broad campaign. Preserve VAPID keys and delivery receipts across deploys. The payment and commission processes do not need a restart for notification-only changes.
## Choosing a pilot audience

New campaigns default to Selected customers. Search opted-in customers by name/email; each row shows the subscribed-device count. Use Select first 50 matching or Select first 100 matching for a pilot, then review/remove individual customers. These buttons replace the selection with up to that many matching customers (newest registrations first), never send anything, and never select non-opted-in/deleted accounts. Clear selection does not mean send to all: an empty targeted draft is rejected in both UI and API. Broad sends require explicitly choosing All opted-in browsers. Selected mode supports at most 100 customers; multiple subscribed devices per customer can make the device count higher than the selected-customer count. Use for test selects a single test recipient; sending still requires the confirmation step. Pilot selection is not random sampling.
